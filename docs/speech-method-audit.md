# Speech recognition method audit

Historical report: generated raw outputs were removed after Phase 5 at the user's request. Numerical summaries and regression sources remain; current behavior is described in [Phase 5](phase5-voice-effects.md) and [casting options](phase4-options.md).

Decision date: 2026-10-13. Target: Minecraft 1.21.1, NeoForge, Java 21, local recognition of a player's own short incantations. No external process, cloud speech API, model download, or general transcription is required by the selected implementation.

## Decision made before implementation

**Use personalized MFCC features and band-limited dynamic time warping (DTW), implemented in Java, with global compact search and enrollment-derived cutoffs.** Store up to ten recordings per spell on disk. Recognize isolated incantations after an energy-based voice activity detector ends the phrase. Search a compact descriptor index of all trained spells, load the best eight acoustic candidates for full DTW, and include equipped candidates. Check cast eligibility after finding the global winner. An unequipped known incantation must never be reassigned to the nearest equipped spell. The spell identifier comes from Iron's spell registry rather than from an English dictionary. This makes names from other addons eligible without a per-addon vocabulary.

This is the smallest deployable baseline among the audited options, judged from its explicit storage/computation bounds and dependency requirements. It is **not a measured claim that MFCC/DTW has the highest accuracy, or that Java beats optimized C/Rust**. Personalized templates can confuse similar incantations, and MFCCs are sensitive to microphone/noise changes. Ten recordings are enrollment examples, not a guarantee of recognition. Reject uncertain matches and collect held-out recordings plus ordinary conversation before tuning acceptance thresholds.

## Java, C and Rust audit

The acoustic algorithm determines most work. Java can implement the same FFT, filterbank and DTW as C/Rust and runs in Minecraft's existing JVM. A C or Rust implementation could use SIMD and finer allocation control, but that advantage must be measured with the same audio/candidate bank. It adds JNI crossings, architecture-specific assets, signing/extraction/loading concerns, and failures outside the JVM's memory-safety boundary. No universal speed ranking is justified without that controlled benchmark. Rust offers safer internal native memory handling, but its JNI interface still needs lifecycle and binary compatibility testing.

The selected Java code uses a radix-2 FFT rather than a naive DFT, 25 ms windows and 10 ms hops at 16 kHz, 26 mel filters, 13 cepstral coefficients excluding energy plus 13 deltas, and two-row bounded DTW rather than a full cost matrix. A low-pass decimator handles Simple Voice Chat's 48 kHz PCM input. It neither owns a microphone nor cancels voice-chat events; Simple Voice Chat remains the audio route.

Training/casting work runs on a bounded client worker, with PCM copied before leaving the voice callback. Recordings are stored locally in separate files keyed by a SHA-256 hash of each registry ID; never upload a voice profile to the server. There is no aggregate trained-spell limit in the normal library. Gameplay caches acoustic-only templates for equipped spells. Global search retains compact208float descriptors, and full features for up to eight shortlisted additional spells are loaded transiently. The GUI retains only128 waveform peaks per recording. Writes replace only the modified spell's file. A recognized ID is only a request: the server must still enforce equipped-spell ownership, level, mana, cooldown, rate limits and Iron's normal casting behavior.

## Acceptance and limitations

- Use distance rejection and a runner-up margin; the nearest template alone is not evidence a phrase was spoken. A bank with indistinguishable labels must reject.
- Bound phrase length to three seconds and ten examples per spell. Discard overlong speech until silence, instead of splitting conversation into apparent commands.
- Runtime full-feature memory scales with equipped spells plus the temporary shortlist. Eight equipped one-second trained spells need about 0.778 MiB feature primitives; eight extra shortlist spells add at most another 0.778 MiB at the same duration. The global index adds about 8.13 KiB per trained spell at 10 takes. Per-spell raw reads/writes temporarily require at most960,000 PCM bytes (about 0.92 MiB). The GUI's ten128-bin previews need about 5 KiB. Java object overhead, extraction workspace and GC are additional costs; these are storage bounds, not measured process RSS.
- Enrollment rejects silence and recordings outside supported lengths. Features and recorded PCM are immutable snapshots.
- Pitch-changing output must happen after recognition; matching the raw local microphone against a pitch-shifted template would degrade accuracy. Real-time voice effects remain future work.
- Evaluate held-out speech, noise, microphone variation, different speaking speeds and ordinary conversation; measure false activations per hour as well as recognition accuracy and p50/p95 latency. Synthetic audio checks algorithm behavior and runtime only.

## Local benchmark and validation

Final alpha.2 run on 2026-10-14 using Java 21.0.12, Windows 11 amd64, Intel Core Ultra 9 285H, with 16 processors available to the JVM. Parallel development jobs had finished before this run. Each case warms up for 60 passes then measures 250 passes with synthetic one-second PCM at 48 kHz, including downsampling, feature extraction and matching. Thread CPU time is CPU consumed per recognition, not machine utilization. Primitive template bytes include features only, excluding Java headers, global descriptors and JVM/working memory.

The latest Gradle run completed 46 tests without failures: 16 speech core tests, 3 offline WAV/manifest tests, 3 preparation tests, 6 streaming-harness tests, 3 legacy profile tests, 5 per-spell library tests, 2 signature-sidecar tests, 2 full-feature sidecar tests, 2 waveform-preview tests and 4 voice-chat lifecycle tests. `SpeechDatasetTool` evaluates ten supplied WAV takes per spell using seven enrollment takes and three held-out takes, optionally checks isolated negative clips, and can import all ten to the local profile format. `SpeechDatasetPrepare` uses Java-only decode/downmix/windowed-sinc resampling and conservative silence trimming to produce derived 16 kHz mono PCM16 WAVs. Original recordings remain unchanged. Prepared private audio is ignored by Git.

## Real recording evidence and architecture revision

The user supplied 100 spell recordings across ten spells. All were 44.1 kHz stereo PCM16; source durations were 0.894–2.015 s (mean 1.320 s). Derived recordings retain 80 ms before and 120 ms after the energy boundary; mean resulting duration was 0.551 s (range 0.340–0.980 s). All recordings fit the three-second limit after format conversion; trimming removes recording-edge silence and is not driven by the recognition label.

Takes 01–07 were enrollment data, takes 08–10 were evaluation data. The initial equipped-only matcher had a serious rejection flaw: it correctly accepted 21/30 utterances and rejected nine, but speaking a known unequipped spell caused 13/30 false casts with nine wrong candidates, and 249/270 false casts when a single wrong spell was equipped. This disqualifies that initial architecture for automatic casting.

The revision derives each spell's cutoff solely from training-take leave-one-out nearest distances: 1.6 times the 90th percentile, bounded to 0.004–0.08. Relative runner-up ratio remains 0.78; minimum score margin uses 0.06 times the training median, bounded to 0.0005–0.004. Fewer than three usable examples use a stricter fallback. Compact global temporal descriptors shortlist eight spells for full DTW; equipment is checked after the global result. This rule was fixed before the revised evaluation, with no cutoff grid search on the 30 evaluation labels.

| Metric | Initial equipped-only matcher | Revised global/calibrated matcher |
|---|---:|---:|
| Correct accepted spell requests |21/30(70%)|27/30(90%)|
| Incorrect accepted spell requests |0/30|0/30|
| Uncertain utterances rejected |9/30|3/30|
| Known unequipped spell,9 other candidates |13/30 false accepts|0/30 false accepts|
| Single wrong equipped spell |249/270 false accepts|0/270 false accepts|

Aggregate outputs: baseline, revised. Revised warm in-memory evaluation measured 1.386 ms p50 and 3.283 ms p95 per utterance; it includes coarse selection and extraction but excludes disk I/O and live SVC delivery. Because the baseline evaluation informed the architecture change, these 30 clips are **development holdouts**, not an untouched final test set. Three uncertain clips remained rejected. That earlier run preceded the negative recordings; the separate frozen negative validation is described below.

The final alpha.2 runtime-shaped evaluation reproduced the same accuracy and known-unequipped results with real per-spell files and sidecars. It measured 0.792 ms median / 1.239 ms p95 for ten equipped spells using the warm full-feature cache, and 5.143 ms median / 6.674 ms p95 for disk-loaded inactive shortlist features. Initial acoustic-cache construction took 71.281 ms across ten spell files; warm matches read no raw PCM. It counted 271,544 feature bytes and 58,240 descriptor bytes for the 70 enrollment examples, with zero retained PCM. The earlier cache run is preserved. Full preparation, architecture changes, limitations and evidence are described in [real-speech-validation.md](real-speech-validation.md).

## Positive-only generic tuning and reserved negatives

The 2026-10-14 extension compares nine generic alignment/calibration variants using the supplied negative recordings only for evaluation. The [full tuning table](generic-recognition-tuning.md) explains why the baseline remains selected: alternatives lost intended casts, added wrong casts, or failed to reduce false matches. The release removes duplicate query feature extraction and keeps the default DTW computation fast without changing score rules. Players enroll only their own spell incantations; no negative recording, dictionary entry or addon-specific rejection example is required.

Untrimmed original positives through the runtime 20 ms/VAD/PTT path produced 25/30 correct development casts, with zero wrong casts. After the rule was frozen, the reserved 40 near-match clips produced 8 false casts with seven enrollment takes or 6 with ten takes; 19 utterances were emitted and 21 clips produced none. The five reserved gameplay files (120.23 s) emitted ten utterances and no casts; two files emitted none. These are limited one-speaker results, not cross-speaker accuracy or a normal-play rate. Full tables and file-level evidence are in [the real speech report](real-speech-validation.md).

An equipped spellbook in Iron's native Curios slot is required before command audio is copied or processed. The server also rejects no-book requests. This gate implements the expected gameplay behavior; acoustic confusion still exists while a book is equipped. Explicit Grimoire enrollment can read/save local recordings without a book. Its ten compact waveform previews use 5 KiB of primitive data; recorded PCM is not retained during gameplay.

- [Hazen et al., query-by-example spoken term detection, MIT](https://people.csail.mit.edu/hazen/publications/Hazen-ASRU-2009.pdf): template queries, multiple examples and DTW matching for low-resource speech.
- [Menon et al., Interspeech 2018](https://www.isca-archive.org/interspeech_2018/menon18_interspeech.html): DTW works with recorded keyword examples; neural matching is faster on their much larger broadcast-search workload. This warns against scanning an unbounded bank every frame.
- [Cho et al., fast enrollable streaming KWS, Interspeech 2023](https://www.isca-archive.org/interspeech_2023/cho23b_interspeech.pdf): learned embeddings, streaming reuse and user-defined enrollment; its server-side training workflow is not copied here.
